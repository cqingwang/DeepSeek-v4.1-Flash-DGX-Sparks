Cause and repair of mesh failure
--------------------------------
Physical links were up, but the four hosts still had old `/opt/dsv41-mesh/mesh-up.sh` and
`mesh-down.sh` state, with routes and `tc flower` destination MACs inconsistent with the
current two-plane sparkring topology. This caused `ibv_modify_qp(RTR): Connection timed out`;
it was a stale L2/L3 mesh-programming issue, not a missing direct connection between every pair.
The configured TP4 order is A -> C -> B -> D. Per-node port orientations are asymmetric, so
non-neighbor ranks are reached through their physical neighbors; no full-mesh assumption was
used. The old scripts were backed up on each host under
`/var/backups/dsv41-mesh/20261006-tp4-a-c-b-d/`, stale routes/rules were removed, and local
planner-generated scripts were installed and started on all four hosts. `dsv41-mesh.service`
is active on every host, and routes plus hardware flower rules match the planner's adjacent-peer
map. Four HCA slots use B12X RoCE GID 3; NCCL's separate `NCCL_IB_GID_INDEX=-1` override is
preserved.

Before model start, corrected A-to-B routed RDMA probe used matching `-x 3 --flow_label=16383`
on both ends, `-s 61440 -n 100`: mean 10.56 us, typical 10.54 us. The D-side forwarding rule
was `in_hw in_hw_count 1`; the observed probe added 1,807 hardware packets / 6,988,386 bytes
and zero software packets. The earlier stale-mesh QP timeout was resolved.
