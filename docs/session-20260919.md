## Measured, new

**Clock cap is nearly free.** Same probes capped at 2200 vs uncapped:

| probe | capped | uncapped | cap cost |
|---|---:|---:|---:|
| prose decode tok/s | 44.6 | 45.3 | 1.5 % |
| code decode tok/s | 102.7 | 103.4 | 0.7 % |
| prefill 8k tok/s | 4,280 | 4,353 | 1.7 % |
| prefill 32k tok/s | 4,153 | 4,373 | 5.0 % |
| prefill 120k tok/s | 3,982 | 4,044 | 1.5 % |

The engine is bandwidth-bound, so a 15 % SM-clock cut costs ~1-2 % on decode. Keep the cap; earlier
uncapped tables are only ~1-2 % optimistic, not 10-15 %.

**Markov head rank, priced** (one GB10, real TP4 shard 32320 x rank, bf16, x5 per step):
rank 256 (today) 0.108 ms/step at 712 GB/s; 320 0.131 (+0.04 % of a step); 384 0.210 (+0.20 %);
448 0.515 (+0.79 %); 512 0.641 (+1.03 %); 1024 1.306 (+2.31 %); 2048 2.797 (+5.19 %).
The head is free only while it fits the 25.2 MB L2 - train a bigger drafter at rank 320-384 first.

|---|---:|---:|---|
| prose | 2.30 | 0.256 | 35 % / 28 % / 20 % / 11 % / 4 % / 3 % |
| prose, thinking on | 2.61 | 0.322 | 29 % / 31 % / 17 % / 8 % / 4 % / 11 % |

Acceptance is flat across concurrency (prose 2.30 / 2.46 / 2.51 / 2.39 at c=1/2/4/8; code 5.26 -> 5.44),
so there is no load-driven adaptation to exploit - the prose gap is the drafter, not the scheduler.

**Prefix cache works.** 35,271-token prompt: first TTFT 8.36 s, exact repeat 0.33 s with 35,072
cached tokens, and a real second turn (history + new question) 0.36 s. Long conversations are cheap.

**Decode does not care about context length.** 400-token prose completion: 50.4 tok/s at 12 prompt
tokens, 51.1 at 14k, 49.9 at 59k, 49.9 at 247k resident.

**Engram row cache** reaches 99.8 % hit rate in steady state (85.4 % in the first minute after boot).

**A long prefill still freezes the fleet.** Two decoders at 46.1 tok/s solo drop to 7.8 tok/s for the
60 s that a 231k-token prefill runs (chunk 4096). Chunk 1024 makes it worse, not better.

**Fresh-boot prefill baseline** (unique prefixes, thinking off, uncapped clock, for the long-uptime check):
7,018 tok -> 3,371 tok/s; 30,020 -> 3,862; 57,019 -> 4,383; 119,019 -> 4,089; 231,018 -> 3,909.

**Concurrency at the capped clock** (per stream, thinking off): prose 45.9 / 35.0 / 26.4 / 17.8 and
code 96.8 / 74.2 / 56.0 / 42.8 at c=1/2/4/8; code aggregate 342 tok/s at c=8. Quality gate 72/75.

**Thinking off is 3.9x faster and just as correct on this set.** The 30-prompt hard set:

| mode | wall | answer tokens | thinking tokens | verifiable answers |
|---|---:|---:|---:|---|
| DS thinking off | 172 s | 11.3k | 0 | all correct |
| GLM-5.3-Flash NVFP4, effort high | 324 s | 15.6k | 4.9k | all correct |
| DS thinking on (our client default) | 671 s | 49.1k | 39.1k | all correct, 6 hit the 4096 cap |

Our OpenCode profile sends `reasoningEffort: high` -> thinking on, so everyday chat pays 4x for
nothing on this class of task. Use a low-effort variant for chat and keep thinking for hard problems.

**Sampling costs about 5 %.** Same prose prompt: greedy 45.2 tok/s, temperature 0.7 -> 42.9, temperature 1.0 -> 43.0.
Every table in the repos is greedy, so real chat with sampling runs a few percent slower than published.

## Draft capture repaired, 2026-09-20

The offline-training tap (`adapter/draft_capture.py`, wraps `TargetVerifyExecutor.commit_hidden`)
looked dead: armed at boot, trigger file in place, live traffic flowing, and the shard count in
`/state/draft-capture` never moved. It was writing the whole time. The shard counter restarts at 0 on
every boot and the writer reuses one flat directory, so each run silently overwrote the previous
one's files (a fresh boot clobbered `shard-000000..000322` of a 4732-shard capture from 2026-09-13).

Fixed by giving every engine run its own directory, `run-<date>-<pid>/`, with a `meta.json` recording
topk, fp8, block size and the folded-sampling mode. Verified: a 500-token sampled answer produced 231
shards / 22 MB in a fresh run directory while the older capture stayed intact.

Measured while repairing:

| property | value |
|---|---|
| hook cost (`DSV41_DRAFT_CAPTURE_BENCH=1`) | 0.249 ms per step, ~0.5 % of a 51 ms step |
| skip counters over 300 calls | armed 0, rank 0, graph 0, kwargs 0, compact 0, hidden 0, stopped 0 |
| data rate | ~110 KB per decode step, ~45 KB per generated token |
| 400 GiB cap | about 9.5 M generated tokens |

It captures under the production `SGLANG_DSPARK_FOLDED_SAMPLING=2` as well; the adapter's own docstring
warns it is blind to all-greedy batches, which is why greedy probes (temperature 0) record nothing.
Collect with sampling on, which is what live traffic uses anyway.
